## 3. 取得元レビュー

### 3.1 現在の取得方式と負荷

- 認証情報を使わず、公開されている空き照会画面だけを取得する。
- 自動予約、予約取消、決済、利用者登録は行わない。
- 対象は3施設、直近15日間の土日祝、8:00〜13:00である。
- workflowはJST 07:07〜23:37の30分間隔で、1日34回のscheduleを持つ。
- 1run当たり最大45施設日、1日当たり最大1,530施設日を処理する。
- 実HTTP request数は、HTML、JavaScript、画像等のsubresourceと再試行により
  施設日数より多くなり得る。
- 同時並列取得はせず、施設・対象日を順番に処理する。

取得元へ確認し、現在の公開空き情報の自動確認・表示・通知について利用許可を取得した。

### 3.4 許可取得後の継続確認事項

1. 認証不要の公開空き照会だけを対象とし、認証・予約・取消・決済を自動化しない。
2. 現在の時間帯、頻度、対象日数、逐次実行を大きく変更する場合は許可範囲を再確認する。
3. 施設名、日付、コート名、空き時間以外の情報を新たに取得・表示しない。
4. 公式予約サイトのリンク条件またはURL構成が変わった場合は追随前に確認する。
5. HTTP 403/429、maintenance、連続失敗、応答時間悪化を検知したら取得を抑制・停止する。
6. 利用規約、robots、公開範囲、運営主体が変わった場合は運用判断を再確認する。

許可回答の原文や担当者の個人情報はリポジトリへ保存しない。
運用上必要な許可範囲、アクセス条件、確認日だけを非公開の運用記録で管理する。

### 3.5 scheduled runの再開

利用許可取得済みのため、次の順でscheduled runを再開する。

1. `ENABLE_SCHEDULED_RUNS=true`へ戻す。
2. productionで1回のmanual-liveを実行する。
3. source revision、テスト、取得、照合、enqueue、dispatch、Pages deployを確認する。
4. 最初のscheduled-liveを確認する。
5. HTTP 403/429、連続失敗、実行時間、request数を本書4節の指標で監視する。

## 4. 鹿児島βの最小運用指標

評価期間はrolling 14日とし、個人情報をGitHubや公開Artifactへ保存しない。
利用者が少ない間は率だけで判断せず、失敗1件ごとに原因を確認する。

| 分類 | 指標 | 初期判断基準 |
| --- | --- | --- |
| 実行品質 | scheduled-liveの成功・失敗・skip | failureは毎回調査し、未解決のまま次Phaseへ進めない |
| freshness | `generated_at`からの経過 | 60分超を遅延、120分超を停止として扱う |
| 取得品質 | 施設日ごとのsuccess/error/fallback | 同一取得元で2run連続失敗したら自動取得を停止して調査 |
| 通知速度 | 検出時刻からprovider acceptedまで | p95 10分以内を目標とし、超過を記録する |
| 通知品質 | 重複、誤配信、別利用者情報露出 | すべて0件を必須とする |
| 配信品質 | accepted/delivered/failed/bounced/complained/suppressed | failure、bounce、complaintは1件単位で確認する |
| 利用状況 | active会員、有効条件、match、通知件数 | 集計値だけを週次で確認する |
| 利用者報告 | 誤検知、見逃し、分かりにくさ | 問い合わせを匿名化して原因と改善を記録する |
